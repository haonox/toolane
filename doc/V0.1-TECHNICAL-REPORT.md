# Toolane V0.1 阶段技术报告

> 编写日期：2026-10-14
> 代码审查基线：`feature/v01-acceptance` 分支的 `d7b93ab`
> 状态：V0.1 自动化验收候选，等待维护者代码审查和阶段确认。本报告描述当前实现，不代表发布或生产可用性结论。

## 1. 阅读范围与结论

Toolane 当前是一个**进程内、本地、异步工具执行原型**。调用方先在服务端注册工具，创建 `Manager`，再通过 `Submit` 提交 JSON 参数；Manager 负责有界排队、固定数量 Worker、执行状态、取消、超时和结果保留。已接入可控的 Mock 执行器和只运行预先注册程序的 Linux Process 执行器。CLI 只演示这两个后端。

从需求范围看，V0.1 指定的单机闭环和 ACC-01～07 已有自动化测试。验收记录在 [`docs/V0.1-ACCEPTANCE.md`](../docs/V0.1-ACCEPTANCE.md)。这些测试支持“当前代码在所测条件下通过”的结论；长时间运行、敌对进程、安全隔离和生产服务能力尚未得到证明。

审查时建议先读 [需求书](../REQUIREMENTS.md) 的 V0.1 范围、状态与验收矩阵，再按第 10 节的代码顺序检查。此报告中的路径均相对于仓库根目录。

## 2. 交付边界

| 项目 | 当前实现 |
| --- | --- |
| 语言与依赖 | Go 1.27.1；`go.mod` 只使用标准库。 |
| 调用方式 | `internal` 包提供进程内 Go API；`cmd/toolane` 提供 Mock/Process 演示。 |
| 执行模型 | 固定 Worker、有界 FIFO 等待队列、每个运行任务一个执行 Context。 |
| 工具来源 | 服务端显式注册；请求只指定已注册工具名与参数。 |
| 后端 | `mock.delay`；Linux 上的可信本地 Process。非 Linux Process 返回 `process_unsupported`。 |
| 数据 | 任务记录和结果保存在内存；终态记录按数量淘汰；进程退出即丢失。 |
| 身份 | `TenantID` 固定为 `local`；`AgentID` 是来源标记，不是认证凭据。 |
| 未实现 | HTTP API、DAG、Docker、持久化、认证、跨租户隔离、SSE、自动重试和生产级监控。它们属于后续阶段。 |

需求书还包含 V0.2 之后的设计约束，不能把那些文字当成已实现功能。当前没有对外稳定的网络协议，也没有外部用户输入可信性的安全边界。

## 3. 结构与依赖方向

```text
cmd/toolane/main.go  演示入口与组装
       │
       ├── internal/tool/registry.go       工具契约、注册、策略
       ├── internal/execution/             准入、FIFO、状态、Worker、结果
       │             │
       │             └── 只依赖 tool 的契约，不依赖具体后端
       └── internal/executor/
                     ├── mock/            可控延时与失败
                     └── process/         可信 Linux 进程、输出预算
```

`tool.Definition` 把 `Validate` 与 `Execute` 显式绑定到工具名。`Registry` 拒绝缺少名称、校验器、执行器的定义，拒绝重复名称和非法工具策略。`NewManager` 复制注册表的映射并计算每个工具的有效策略；之后向原注册表添加工具，不会改变已创建的 Manager。参见 [`internal/tool/registry.go`](../internal/tool/registry.go) 与 [`internal/execution/policy.go`](../internal/execution/policy.go)。注册表复制的是定义值；其中的函数仍是注册方提供的代码，应由服务端负责其行为。

Manager 不认识 `mock` 或 `process` 包。执行器返回 `tool.Outcome`（结果、输出、退出码、启动时间、停止确认情况）和 `error`；最终状态由 Manager 裁决。`tool.RunError` 允许后端附带稳定错误码，而不用让 Manager 导入具体后端。这个边界使状态规则可以用可控执行器测试，进程行为可单独集成测试。

## 4. 一次任务如何运行

1. **注册与创建**：调用方创建 `Registry`、注册 `Definition`，调用 `NewManager(Config, Registry)`。配置和工具策略校验失败会直接返回错误；成功后启动固定数量 Worker、一个排队期限监视 Goroutine 和一个等待关闭的 Goroutine。
2. **准入**：`Submit` 检查调用 Context、Agent ID、工具名、请求时限与输出上限、参数字节长度；在复制参数后调用工具的 `Validate`。随机 128 位 ID 生成后，持锁检查关闭/后端停止/队列容量，写入 `queued` 记录。满队列返回 `ErrQueueFull`，不增加记录。
3. **认领**：Worker 在 Manager 锁下从 FIFO 队头取任务。若等待期限已过，直接记为 `timed_out`，不调用执行器；否则设置 `running`、开始运行期限、占用一个槽位，然后在锁外执行工具。
4. **执行**：Manager 把有效输出上限与两个回调传给执行器。`OnOutputLimit` 请求停止，`OnProcessStarted` 记录实际启动时间。执行器必须在取消后停止自己拥有的工作，返回时才视为结束。
5. **完成与保留**：Manager 持锁处理执行结果、裁决终态、释放运行槽位。终态记录超过 `RetainedResults` 时按完成顺序淘汰最旧记录；`Get` 返回快照复制，淘汰后返回 `ErrNotFound`。

`Submit` 的 Context 只控制是否接受请求；接受后的任务 Context 由 Manager 在认领时创建。调用方的请求 Context 后续取消，不会自动取消已接受任务。这一点由 `TestSubmitContextDoesNotOwnAcceptedWork` 验证。参见 [`internal/execution/manager.go`](../internal/execution/manager.go) 与 [`internal/execution/worker.go`](../internal/execution/worker.go)。

## 5. 状态、时间与停止裁决

```text
queued ──认领──> running ──完成──> succeeded / failed
   │                │
   ├─取消──────────> cancelled
   └─排队超时──────> timed_out
                    │
                    └─取消 / 运行超时 / 输出触限 / 关停──> cancelling
                                                          │
                                                          ├─取消或关停──> cancelled
                                                          ├─运行超时────> timed_out
                                                          └─输出触限────> failed
```

状态变更由 Manager 的同一把互斥锁保护。`Cancel` 对排队任务直接提交终态并移出队列；对运行任务先写 `cancelling` 和 `user_cancelled`，解锁后调用 `cancel()`。重复取消及已完成任务的取消不会覆盖既有结果。运行期限由认领时的 `context.WithTimeout` 计时；排队期限由 `Submit` 的接受时刻计时，统一的期限监视器负责清理尚未被认领的超时任务。`Close` 停止准入，取消队列和运行中的工作，并等待内部 Goroutine 退出。

竞争的裁决点是**Manager 锁下提交的状态**。停止原因只有在 `running` 时首次写入；迟到的取消、输出触限或超时回调不改写已经提交的原因。`complete` 也会检查 Context 是否到期，以处理期限已触发但回调尚未获得锁的情况。终态一旦提交不再变更。相关定向测试同时覆盖“完成先赢”和“停止先赢”。

时间字段均以 UTC 输出：`CreatedAt`/`ReadyAt` 为接受时间，`RunningAt` 为认领时间，`ProcessStartedAt` 是 Process `cmd.Start` 成功后的时间，`FinishedAt` 是终态提交时间。`queued` 和 `cancelling` 不一定马上变成终态；后者要等待执行器实际返回。

| 停止原因或结果 | 终态/错误码 | 说明 |
| --- | --- | --- |
| 排队超时 | `timed_out` / `queue_timeout` | 不调用执行器。 |
| 运行超时 | `timed_out` / `execution_timeout` | 执行器返回后提交终态。 |
| 用户取消、服务关闭 | `cancelled` / `cancelled` | `StopReason` 分别记录 `user_cancelled`、`service_shutdown`。 |
| 输出达到上限 | `failed` / `output_limit_exceeded` | stdout/stderr 共享字节预算。 |
| 后端错误 | `failed` / 后端 `RunError.Code`，否则 `execution_failed` | Process 常见码有 `process_start_failed`、`process_exit_nonzero`、`process_wait_failed`。 |
| 结果过大或无效 JSON | `failed` / `result_limit_exceeded`、`invalid_result` | 仅处理结构化 `Result`。 |
| 停止无法确认 | 保持 `cancelling`，`CleanupStatus=failed` | 保留运行预留，Manager `Halted=true`，拒绝新提交；`Close` 返回 `ErrStopUnconfirmed`。 |

`CleanupStatus` 在正常路径初始化为 `not_needed`，当前主要用于标记无法确认停止的 `failed`；它不是详细的清理过程审计。`ErrorMessage` 是最多 4 KiB 的诊断摘要，不宜在未来直接当公开 API 错误正文使用，因为底层错误可能包含宿主信息。

## 6. 限额与内存边界

以下是 [`DefaultConfig`](../internal/execution/manager.go) 的默认值，不是性能实测值。配置由服务端创建；单工具 `Policy` 只能收紧全局上限，字段为零时继承全局限制或经工具上限收紧后的默认值。请求可选择不超过有效最大值的等待/执行期限和输出上限，零表示采用默认值。

| 资源或数据 | 默认值 | 计数或处置 |
| --- | ---: | --- |
| 同时运行 Worker | 4 | 认领后到执行器返回占一个槽位。 |
| 排队容量 | 256 | 只计算已接受、尚未认领的任务；满时拒绝。 |
| 可淘汰终态记录 | 1000 | 活跃任务另外保留；超出时淘汰最旧终态。 |
| 排队期限 / 最大值 | 30 秒 / 300 秒 | 接受后计时。 |
| 运行期限 / 最大值 | 10 秒 / 60 秒 | Worker 认领后计时。 |
| stdout + stderr | 1 MiB | Process 采集时共用原始字节预算；Manager 对后端返回值再截断。 |
| 工具参数 | 256 KiB | 在复制前按字节长度拒绝。 |
| 结构化结果 | 64 KiB | 完成时按字节长度检查。 |
| Agent ID | 256 字节 | 在准入时拒绝超额。 |
| 错误摘要 | 4 KiB | 保留前截断并修复无效 UTF-8。 |

上界是各类别的局部约束，不等于一个固定的进程 RSS 上界：已接受任务包含各自参数和元数据，运行后端会有自己的工作内存，Go 运行时也有开销。`Validate` 在入队前执行，由注册方提供，其成本由工具实现决定。对于返回超长字符串的自定义执行器，Manager 能限制**保留**的 stdout/stderr，但不能阻止执行器在返回前自行构造这些字符串；Process 后端则在读管道时限流。输出达到预算（含刚好达到）即标记并请求停止。

`Snapshot` 的 `Result` 和指针字段会复制后返回，避免调用方修改 Manager 内部记录。有效限制值存于 Go 快照，但 JSON 标签为 `-`，CLI 输出不会显示它们。`Stats` 是瞬时观测值，不提供后续容量预留。

## 7. Process 后端的资源所有权

[`internal/executor/process/process.go`](../internal/executor/process/process.go) 的 `Spec` 由服务端持有：要求显式 `Trusted=true`、绝对路径可执行文件、参数构造函数；工作目录如设置也必须为绝对路径。请求不能直接选择可执行文件、工作目录或环境变量。`Args` 产出参数数组，执行使用 `exec.Command`，不拼接 Shell 命令。环境变量采用 `Spec.Environment` 的显式列表；若为空，子进程得到空环境。构造时复制环境切片；`Args` 函数本身仍由注册方负责。

Linux 实现在 [`run_linux.go`](../internal/executor/process/run_linux.go)：

1. `cmd.Start` 成功后记录真实启动时刻，并由一个 Goroutine 执行 `cmd.Wait`。
2. `Setpgid=true` 为命令创建独立进程组。取消/超时时先向组发送 `SIGTERM`，宽限期默认 2 秒；父进程仍未退出则发送 `SIGKILL`。
3. 父进程 `Wait` 返回后再向该组发送 `SIGKILL`，处理父进程先结束、普通子进程仍存活且已关闭管道的场景。
4. 进程组发信号失败时尝试直接杀死父进程，并把 `StopUnconfirmed` 交给 Manager；Manager 不释放该任务的运行预留，暂停新任务准入。

`CleanupTimeout` 默认 5 秒，代码把它与宽限期的差额设置为 `exec.Cmd.WaitDelay`，用于限制 `Wait` 在管道等场景的附加等待。**它不是进程执行和清理整体的硬截止时间**：若内核无法停止进程、执行器卡住，`Close(ctx)` 的 Context 只限制调用者等待时间，不能替代实际停止确认。`CleanupStatus` 也没有逐步记录 TERM/KILL/Wait 的过程。

此方案只针对可信程序和留在同一进程组的普通后代。主动脱离进程组的后代、不可中断的内核等待、敌对代码、文件系统/网络权限隔离均不在保证内。当前 Process 是本机执行，不是沙箱。非 Linux 实现见 [`run_other.go`](../internal/executor/process/run_other.go)。

输出由 [`output.go`](../internal/executor/process/output.go) 中的共享 `outputBudget` 接收。stdout/stderr 可并发写入，互斥锁保护剩余额度，`sync.Once` 确保触限回调只调用一次；额度外数据被丢弃，但仍消费管道以利退出。预算按原始字节计，转成文本时无效 UTF-8 被替换为 `?`。两路输出各自的文本可读，但不能据此恢复其跨流到达顺序。

## 8. Mock 与 CLI 的作用

[`internal/executor/mock/mock.go`](../internal/executor/mock/mock.go) 注册 `mock.delay`：参数为 `delay_ms`（0～60000）、`fail` 和 `value`。执行时按 Context 可取消地等待，成功返回 `{"value":...}`，`fail=true` 返回错误。它提供低成本、可控制的生命周期验证，不模拟进程清理或系统资源隔离。

[`cmd/toolane/main.go`](../cmd/toolane/main.go) 组装 Registry 和 Manager，默认运行 Mock；`go run ./cmd/toolane process` 使用系统 `printf` 做可信 Process 演示。入口每 20 毫秒查询一次结果，5 秒后停止等待，并在退出时关闭 Manager。它是示例程序，不接受任意工具注册、外部请求或持久运行服务。仓库根目录执行：

```bash
go run ./cmd/toolane
go run ./cmd/toolane process
```

建议审查时特别判断以下设计选择是否符合项目下一步方向：

- 自定义执行器的契约要求“取消后停止自身工作再返回”；Manager 无法强制停止任意 Go 函数。未来若引入第三方工具，需要重新界定信任与隔离。
- `Validate` 与 Process 的 `Args` 在准入和执行阶段各调用一次；它们应是确定性、无外部副作用的服务端函数，否则两次结果可能不同。
- `StopUnconfirmed` 使整个 Manager 暂停准入并保留槽位。这是一种偏保守的资源处理，未来多后端时是否细化到具体后端，需要设计决定。
- 当前输出预算按字节触发，刚好达到上限也停止；单工具策略、结果淘汰数量、错误摘要长度都是对调用方可见的行为，修改时应同步测试和文档。
- 没有存储恢复机制。任何跨重启“任务仍可查询”或“恰好执行一次”的表述都不成立。

## 11. 维护者验收建议

本报告所述代码具备供 V0.1 审查的完整单机执行闭环。维护者可以按第 10 节逐文件检查，并在 Linux 环境复现第 9 节命令；特别关注状态竞争、进程清理和不可信输入边界。如果这些实现选择与测试覆盖得到认可，可以确认 V0.1 阶段；若发现契约偏差，应先在当前阶段修正并补相应回归测试，再进入 DAG 或 Docker 阶段。
