# V0.3 第三批：沙箱残留回收与故障隔离

本批在固定镜像 Docker Executor 上增加按部署实例归属的回收。它处理正常执行后删除失败和上次进程退出留下的容器；容器任务记录仍只保存在内存中，因此重启回收只负责停止、删除资源，不会重跑任务或还原旧执行结果。

## 启动和关闭顺序

共享相同镜像策略的 Docker 工具应共用一个 `docker.Backend`；不同镜像策略需使用不同的 `InstanceID`。`InstanceID` 必须在服务重启后保持稳定，并且不能与其他同时运行的 Backend 或部署复用。创建 Manager、开放准入前先调用 `Recover`；正常关闭时先关闭 Manager，再关闭 Backend。

```go
backend, err := docker.NewBackend(docker.Spec{
    ImageTag:    "alpine:3.24.2",
    ImageDigest: "sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6",
    InstanceID:  "local",
})
if err != nil {
    return err
}
if err := backend.Recover(ctx); err != nil {
    return err // 停止无法确认或残留达到上限时暂停准入
}
definition, err := backend.Definition("sandbox.shell")
if err != nil {
    return err
}
if err := registry.Register(definition); err != nil {
    return err
}
// 关闭时：先 manager.Close(ctx)，再 backend.Close(ctx)。
```

原有 `docker.ScriptDefinition` 仍可用于单工具注册，并在首个任务执行前扫描残留；显式 `Backend` 接口适合需要在开放准入前确认恢复结果的服务。`Recover` 会跳过该 Backend 正在执行的任务，扫描时只匹配项目和实例标签，并在删除前核验容器名称及 Execution 标签。

## 资源上限和状态

- 删除失败且已确认容器停止时，任务可以进入终态，`cleanup_status` 先记为 `pending`。后台最多重试 3 次，每次间隔 1 秒、单次清理有 5 秒期限；结果通过回调更新为 `succeeded` 或 `failed`。`cleanup_error` 保留或清除对应诊断，不覆盖脚本执行结果。
- 每个 Backend 最多跟踪 16 个待清理容器。达到上限时拒绝新的沙箱执行；`RecoveryStatus` 返回待清理数量、阻塞标志和最近一次错误。重启扫描发现残留后按相同上限处理。
- Docker 不可达、归属不符或停止状态无法确认时，回收失败并拒绝新任务。运行中停止无法确认时，Manager 保持 `cancelling`、CPU/内存预留与停止准入；需要运维排查，不会自动释放无法证实已停止的资源。
- 单次 Docker 控制命令的 stdout/stderr 各限制为 1 MiB，防止异常 daemon 响应无限占用内存。后台重试数量、间隔和时间均有上限；重试耗尽的容器仍保留标签，下一次 `Recover` 可以继续处理。

## 验证

单元及故障注入测试覆盖按实例归属回收、活跃任务跳过、删除失败重试、残留上限、Docker 失联后的停止确认和任务快照更新。真实容器测试覆盖 OOM 分类、运行中超时停止，以及两个不同实例的残留容器只回收目标实例。运行命令：

```bash
go test ./...
go test -race ./...
go vet ./...
sudo env PATH="$PATH" GOCACHE=/tmp/toolane-v03-go-cache go test -tags=integration ./tests/integration/... -v
```

2026-10-18，在 Docker 29.9.1、cgroup v2、内建 seccomp 的本机环境中，新增的 OOM、运行中超时和跨实例回收测试分别通过。完整 V0.3 阶段验收将在代码合并后对最终 `main` 再执行。
