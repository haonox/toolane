# V1.0 恢复后的容器清理状态

此前服务重启会扫描实例标签、停止或删除残留容器，并中断重启前已认领的任务；但即使容器已经删除，历史任务仍可能长期保留 `cleanup_status=pending`。这会让查询结果与实际资源状态不符，也会让保留策略持续保护本可清理的记录。

现在恢复回调逐个核对 SQLite 保存的容器 ID。只有 Docker 明确报告该 ID 已不存在，Manager 才在事务中把对应任务的清理状态更新为 `succeeded`，清空旧清理错误并追加 `progress` 事件。原任务的执行终态不改变：重启前运行中的任务仍为 `interrupted/service_restarted`，不会自动重跑。

如果容器仍存在但已停止，启动可继续，清理状态保持待处理。Docker 后端继续有界删除重试；服务以固定间隔检查这些已记录 ID，确认删除后再更新 SQLite。若服务在确认前退出，下次启动会重新核对。容器仍在运行、归属标签不匹配或 Docker 检查失败时，恢复不会把清理标记为成功。

这项协调适用于配置了 Docker 的本地 HTTP 服务。其他直接调用 `NewDurableManager` 的进程内使用者须在恢复回调中仅对确实不存在的资源设置 `RecoveryResource.AbsentConfirmed`，并在后续删除完成时调用 `Manager.ConfirmRecoveredCleanup`。保留策略仍保护未确认清理成功的资源。

验证包括 Manager 持久化单元测试、Docker 所有权单元测试，以及真实 Docker HTTP 服务测试。后者覆盖“容器 ID 已落盘”和“容器已创建但 ID 尚未落盘”两个窗口，并确认已删除的历史容器在 HTTP 查询中显示清理成功。真实容器测试需在可访问 Docker daemon 的主机运行，命令见 [Docker HTTP 服务](./V1.0-DOCKER-HTTP.md)。
