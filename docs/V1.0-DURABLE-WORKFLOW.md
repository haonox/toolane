# V1.0 第六批：持久化 Workflow 运行与恢复

`NewDurableManager` 现在可通过 Go API 提交、查询和取消静态 DAG。`SubmitWorkflow` 在返回前使用第五批的 `CreateWorkflow` 一次提交工作流、全部节点和首个事件。数据库写入失败时不将节点放入内存队列。CLI 仍使用内存 Manager；HTTP 服务与 Workflow 幂等提交入口尚未提供。

## 在线状态

节点认领仍遵守单任务的先落盘、后调用 Executor 顺序。父节点完成时，下游的 `blocked → queued` 或 `blocked → skipped` 会写入节点状态与事件；所有节点终结后更新 Workflow 汇总状态和完成时间。工作流整体取消先提交 `cancelling` 汇总状态，再停止运行节点并终结未启动节点。状态写入失败会暂停新准入。

Workflow 汇总更新与单个节点事件是相邻的独立事务。如果进程恰好在两者之间中断，启动协调会从节点状态重建汇总与下游状态。工具执行结果缺失时不会重跑已认领节点。

## 重启协调

启动时先调用资源回收回调，随后读取 Workflow 与 Execution，重建节点依赖、待启动容量和就绪队列，再启动 Worker。旧的 `running/cancelling` 节点终结为 `interrupted/service_restarted`，失败沿 DAG 跳过下游；未认领的 `blocked/queued` 节点保留原等待期限，过期则终结为 `timed_out`。独立分支继续执行。若崩溃发生在父节点终态已提交、下游尚未更新的窗口，恢复过程补齐下游状态。持久化终态批次在内存淘汰后仍可查询。

本批未实现 Workflow 端点的幂等键、持久化记录清理策略、HTTP/SSE 与服务入口。真实 Docker 的资源回收仍须由调用方提供并在准入前完成；本批测试使用受控工具和临时 SQLite。
