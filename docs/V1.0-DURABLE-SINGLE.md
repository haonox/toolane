# V1.0 第三批：单任务持久化运行路径

这一批新增 `execution.NewDurableManager`，把单任务的提交、认领、取消、超时和最终结果接入 SQLite。原有 `NewManager` 保留进程内模式。当前 CLI 尚未启动持久化服务；这一批通过 Go API 和临时 SQLite 集成测试验证运行路径。

## 启动与准入

调用方先打开 `sqlite.Store`，然后调用 `NewDurableManager(ctx, config, registry, store, recoverResources)`。`recoverResources` 必须确认上次进程留下的所有相关执行资源已停止或不存在；例如为每个 Docker Backend 调用 `Recover`。若资源回收或数据库协调失败，构造函数返回错误，Worker 不启动。一个 Store 同时只允许一个 Manager 拥有运行权；Manager 运行期间 Store 会拒绝关闭，调用方须先完成 Manager 关闭。

单任务 `Submit` 会在返回接受结果前提交任务与首事件。`SubmitIdempotent` 使用已解析的租户、固定提交端点和键查询或创建任务；即使队列已满，有效的重复键仍返回原 ID。参数 JSON 的字段顺序、空白和与显式默认值等价的请求会被规范化；数字的不同词法形式仍视为不同输入。调用方必须从可信身份确定租户，不能直接信任 HTTP 请求体中的租户字段。

Worker 在调用 Executor 前，先提交 `running` 状态和对应事件。这是执行认领意图；持久化失败时任务留在队列，暂停新准入，不调用工具。状态写入和事件追加是同一事务。工具运行中的启动时间与清理更新也会写入进度事件；完成、取消、超时的最终状态提交后才释放运行槽位。数据库故障会暂停准入并暴露错误，需要重启协调。

## 重启语义

启动时先执行资源回收，再读取数据库记录。未认领且未到期的 `queued` 任务按原始等待期限重建队列；已过期的任务终结为 `timed_out/queue_timeout`。旧的 `running/cancelling` 任务不会重跑，在资源停止得到确认后终结为 `interrupted/service_restarted`。终态记录可从数据库查询，即使已从 Manager 的内存保留窗口淘汰。

目前只支持单任务持久化。持久化 Manager 会明确拒绝 `SubmitWorkflow`；Workflow 的持久化、已创建资源 ID 的单独记录、保留策略、HTTP/SSE 和服务入口仍在后续 PR。提交幂等防止重复创建任务，不保证外部副作用只发生一次。

集成测试覆盖提交前落盘、认领前落盘、完成与取消/超时持久化、并发幂等与队列满时重放、重启后排队继续和已认领任务中断、恢复钩子失败时不启动 Worker、认领写入冲突时不运行工具。测试使用受控工具和临时 SQLite；本批不宣称真实 Docker 崩溃恢复已经完成。
