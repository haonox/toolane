# V1.0 第四批：Docker 资源归属持久化

本批衔接[单任务持久化运行路径](./V1.0-DURABLE-SINGLE.md)和 V0.3 的[按实例标签回收](./V0.3-RECOVERY.md)。Docker 创建容器成功后立即调用 Manager 提供的 `OnResourceCreated`；Manager 在一个事务内保存容器 ID、实例 ID、`cleanup_status=pending` 和 `resource_created` 事件。只有事务成功，Docker 才继续检查容器策略并启动容器。资源记录失败时，Docker 不启动容器，改用原有的有界清理流程；停止无法确认时仍保留运行预留并暂停准入。

`NewDurableManager` 的恢复回调现在收到 `[]RecoveryResource`，包含数据库中清理尚未确认完成的资源及所属 Execution。回调必须在开放准入前确认它们已停止或不存在，并扫描部署实例标签。标签扫描覆盖“Docker 已创建容器，但资源 ID 尚未写入 SQLite”时的崩溃窗口。若恢复失败，Worker 不启动，旧任务也不会被误标为已协调。已认领任务在恢复成功后终结为 `interrupted/service_restarted`，不会自动重跑。

调用方必须保持稳定的 Docker `InstanceID`，并确认恢复回调处理了所有已记录实例；只调用某个新实例的 `Recover` 无法覆盖旧实例资源。资源 ID 保存在内部持久化记录中，事件只包含资源类型，不向未来的 SSE 客户端直接公开容器 ID。当前尚无服务入口来组装这些回调；持久化 Workflow、保留策略和 HTTP/SSE 仍未实现。容器已删除但回调未报告清理结果时，记录可能保留 `cleanup_status=pending`，后续清理状态协调仍需完善。

## 验证

```bash
go test ./...
go test -race ./...
go vet ./...
sudo env PATH="$PATH" GOCACHE=/tmp/toolane-v10-go-cache go test -tags=integration ./tests/integration/... -run '^TestDockerDurableRecovery$' -count=1 -v
```

单元测试覆盖资源记录先于工具继续执行、落盘冲突暂停准入、资源写入失败后阻止 Docker 启动并清理，以及恢复回调收到记录。真实 Docker 测试创建两个未启动容器，分别模拟已记录 ID 与创建后尚未记录 ID 的崩溃窗口；测试结束检查两个容器均被回收、任务均为 `interrupted`，且工具没有重跑。真实容器测试的通过情况须以运行结果为准。
