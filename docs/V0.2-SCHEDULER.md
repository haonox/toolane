# V0.2 租户调度与 FIFO 对比

本批次实现 REQ-SCHED 的进程内租户运行/待启动配额、默认轮询调度和 FIFO 基线，覆盖 ACC-10。DAG 的 ACC-08、ACC-09 见 [V0.2 DAG 说明](./V0.2-DAG.md)。阶段确认仍由维护者审查。

## 调度契约

- `Request.TenantID` 和 `WorkflowRequest.TenantID` 由可信进程内调用方提供；省略时为 `local`。`AgentID` 仍只是来源标记，租户 ID 也尚无网络认证含义。
- 默认每租户最多 2 个运行任务和 64 个待启动节点，全局仍最多 4 个 Worker、256 个待启动节点。`blocked` 与 `queued` 都占租户及全局待启动容量。租户待启动额度不足返回 `ErrTenantQueueFull`；工作流整批拒绝。
- 认领任务时，在 Manager 锁内将待启动额度转为运行额度；任务返回后才释放运行额度。`cancelling` 和停止无法确认的任务仍占运行额度。排队取消、超时、依赖跳过和关闭都会释放待启动额度。
- 默认 `SchedulerRoundRobin` 按活跃租户轮询，每次从选中租户取最早就绪任务。达到运行配额或暂时没有就绪任务的租户会被跳过。`SchedulerFIFO` 选择全局最早的**可运行**就绪任务，供同配置实验比较；它也不会让配额已满的租户挡住其他租户。
- 租户只有在存在待启动或运行任务时才保留调度状态；完成后删除。就绪队列和租户列表都由全局容量约束。Mock 与可信 Process 当前按槽位计费；Docker 的 CPU、内存和后端预算属于 V0.3。

实现集中在 `internal/execution/scheduler.go`；Manager 仍拥有状态锁和资源计数，不新增每任务等待 Goroutine。`scheduler_test.go` 使用可控执行器验证轮询与 FIFO 顺序、租户运行上限、跳过不可运行租户、租户容量整批拒绝及额度释放。原有 V0.1 和 DAG 测试继续运行。

## 可复现的 Mock 调度实验

运行：

```bash
go run ./benchmarks/scheduler -out /tmp/toolane-v02-scheduler -repetitions 3 -seed 20261018
```

实验程序保存 `executions.csv`（每次提交一行，包括拒绝）和 `metadata.json`。本次运行的[原始数据](../benchmarks/results/v02-scheduler-2026-10-18/executions.csv)与[环境配置](../benchmarks/results/v02-scheduler-2026-10-18/metadata.json)已保存。环境为 Linux amd64、Go 1.27.1、Intel Core i5-8400（6 核）、`GOMAXPROCS=6`。4 个 Worker、全局待启动容量 256、租户运行/待启动额度 2/64；两种策略使用相同工具、限额、请求列表和随机种子。

四类负载每次各提交 72 个独立任务：短任务每个等待 2 ms，长任务 15 ms，混合任务由固定种子在两者间选择，突发负载为 A 租户 48 个、B/C 各 12 个短任务。前三类每租户各 24 个。请求按 A、B、C 分组顺序提交；执行器入口由同一个闸门暂缓，整批提交后同时放行。因此测的是**已形成积压时的调度机会**，不是开放式到达模型或服务极限吞吐。每组 FIFO 后运行轮询，重复 3 次；没有预热。

下表为 3 次结果的算术平均。Jain 指数按前 24 次认领中 A/B/C 的认领次数计算；“C 首次”是 C 第一次获得认领的序号；等待 P95 按 `running_at - created_at` 的每次近邻秩 P95 求平均。每组 72 次提交均接受，拒绝数均为 0。

| 负载 | 策略 | 前 24 次认领 Jain | C 首次认领 | C 等待 P95 |
| --- | --- | ---: | ---: | ---: |
| 短任务 | FIFO | 0.667 | 49.0 | 57.2 ms |
| 短任务 | 轮询 | 0.976 | 6.7 | 43.7 ms |
| 长任务 | FIFO | 0.667 | 49.0 | 358.1 ms |
| 长任务 | 轮询 | 0.983 | 5.7 | 267.6 ms |
| 混合任务 | FIFO | 0.658 | 45.7 | 164.3 ms |
| 混合任务 | 轮询 | 0.990 | 7.0 | 135.4 ms |
| 突发租户 | FIFO | 0.667 | 26.3 | 28.0 ms |
| 突发租户 | 轮询 | 0.990 | 5.0 | 23.0 ms |

前三类是等量请求，可用早期认领的 Jain 指数观察调度机会；突发负载各租户需求量不同，其指数仅描述前 24 次分布，不代表应长期获得相同 CPU 时间。轮询使 C 更早得到认领，同时会改变 A/B 的等待时间。单机、短时、无预热的 Mock 结果不能作为生产吞吐量或所有负载下延迟改进的承诺；CSV 保留了每个租户的等待、总延迟、状态和拒绝信息供复核。
