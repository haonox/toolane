# V0.2 DAG 工作流：第一批实现

本批次实现需求书的 REQ-DAG 与 ACC-08、ACC-09，以及 REQ-SCHED 中“等待依赖的节点计入待启动容量”的部分。调用入口仍是进程内 Go API。后续批次的租户配额、轮询调度和 FIFO 对比实验见 [V0.2 调度说明](./V0.2-SCHEDULER.md)。

## 接口与边界

- `SubmitWorkflow(ctx, WorkflowRequest)` 提交静态节点参数和显式 `DependsOn`。节点 ID 在工作流内唯一；依赖可在提交列表中先于父节点出现。
- `GetWorkflow(id)` 返回工作流汇总及按提交顺序排列的节点快照。单个节点仍可通过 `Get(executionID)` 查询或 `Cancel(executionID)` 取消。
- `CancelWorkflow(id)` 在同一状态锁内将所有未启动节点标为 `cancelled`，将运行节点标为 `cancelling`，随后请求执行器停止。只有执行器返回后，工作流才终结为 `cancelled`。
- 单任务 `Submit`、`Get`、`Cancel` 保持可用；当前可由可信进程内调用方传入模拟租户 ID，省略时使用 `local`。

工作流在接受时先校验节点数、请求编码大小、节点 ID、依赖存在性与无环性，并逐个应用现有工具参数和有效策略校验。默认最多 64 个节点，编码后请求最多 256 KiB。这两个上限可通过 `Config` 调整。全部校验通过后，Manager 在一个锁区间内检查剩余待启动容量并建立整批记录；容量不足返回 `ErrQueueFull`，不留下部分节点。

`blocked` 与 `queued` 都占用 `QueueCapacity`。等待期限从整批接受时起算，因此依赖等待也消耗该期限；只有节点进入就绪队列时才填写 `ready_at`。Worker 不会认领 `blocked` 节点。所有直接依赖成功后，节点转为 `queued`；任一直接依赖失败、超时、取消或跳过，其下游递归标为 `skipped/dependency_failed`。其他分支继续执行。

工作流全部节点成功时汇总为 `succeeded`；存在非成功节点时汇总为 `failed`；整体取消期间为 `cancelling`，全部节点终结后为 `cancelled`。运行中任务的取消、超时与完成仍按 Manager 锁下首次提交的状态裁决。

## 保留与验证

活动工作流的已完成节点不会单独淘汰。工作流终结后，工作流和全部节点形成一个保留组；结果数量超过 `RetainedResults` 时按完成组顺序淘汰整组，以免留下缺失节点的工作流。若单个工作流节点数已经超过配置的终态保留数量，终结后可能立即被淘汰。

`workflow_test.go` 覆盖无效图全批拒绝、容量不足全批拒绝、多个直接依赖、失败分支传播、独立分支、单节点及整体取消、`blocked` 超时、关闭与整组淘汰。复现命令：

```bash
go test -count=1 ./...
go test -race -count=10 ./internal/execution
go vet ./...
```

工作流只有内存记录，进程退出后无法恢复。本批次自身没有实现认证、Docker 或 HTTP；调度与租户配额已由后续批次接入。
