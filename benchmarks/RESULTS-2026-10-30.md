# 2026-10-30 双机 12 阶段压测与优化记录

## 测试条件与口径

- 服务端：实验室服务器，Intel Core i7-13700KF，24 个逻辑 CPU，约 31 GiB 内存；客户端：实验室工作站。两端均运行 Linux。
- 代码起点为 `4cb4fda`。1,000 个租户、48 个 Worker、4,096 个全局排队位置、50,000 条内存保留记录；负载与阶段顺序见 `config/workload.json`、`config/stages.json`。12 个阶段共计划 198,000 次调用。
- 第一轮使用 SQLite WAL + `synchronous=FULL`，经单条 SSH 本地转发；第二轮使用本次改动的版本、SQLite WAL + `synchronous=NORMAL`，前九阶段经 SSH 转发。两轮各使用一个新数据库，阶段之间复用该数据库，属于增长系列，不是独立容量曲线。
- 第一轮高并发阶段在发现 SSH 服务端进程的文件句柄软上限只有 1,024 后，将其提高到 65,535 再重测；表中使用重测值。第二轮也提高了该上限，但高并发客户端传输错误仍存在。
- 后三阶段因单条 SSH 转发造成大量客户端传输超时，使用只允许工作站源 IP 的临时 TCP 直连转发重测。`ramp-4096`、`overload-6144` 重测将客户端 HTTP 超时从 10 秒改为 30 秒、终态等待从 30 秒改为 60 秒。开放到达率阶段也使用此超时，并将客户端最大在途数从 4,096 提高到 8,192，避免客户端自身丢弃。到达率为约 1,433 次/秒，即第二轮 `ramp-512` 完成速率的 1.5 倍。临时端口在测试结束后关闭。

## 定位与改动

1. 在相同服务器与 512 并发、8,000 次调用的重启对照中，FULL 约 101 次成功/秒，显式选择 NORMAL 约 979 次成功/秒，约提高 9.7 倍。NORMAL 轮的 10 万次调用也全部成功，速率约 989 次/秒。主要瓶颈是每次任务状态提交触发的同步写盘，以及提交、领取、完成期间持有管理器互斥锁；直接运行 Python 工具的独立对照不足以解释 FULL 轮的退化。
2. 代码增加可选的 `database_synchronous: "normal"`，默认仍为 `full`。WAL + NORMAL 可保证应用进程崩溃或普通重启后的数据库一致性与已提交事务，但操作系统崩溃或突然断电时可能丢失最近提交的事务；需要断电级持久性的部署应继续使用 FULL。此取舍依据 [SQLite 官方说明](https://www.sqlite.org/pragma.html#pragma_synchronous)。
3. 成功的执行状态 GET 轮询改为 Debug 日志；状态查询命中内存时使用读锁。服务端完整矩阵日志由 FULL 轮约 2.2 GiB 降至 NORMAL 轮约 146 MiB。单独的日志对照未证实吞吐改善，因此不把吞吐提升归因于日志改动。
4. 单条 SSH 隧道在 4,096 并发时，服务端接收的任务最终全部成功，但客户端出现大量轮询传输超时；服务器本机回环对照 4,096/4,096 成功且无传输错误。直连重测后 `ramp-4096` 观测到 11,992/12,000 成功。原高并发结果主要受测试链路限制。
5. 原开放到达率阶段的客户端最大在途数 4,096 导致未提交请求；增至 8,192 后，12,000 次计划到达全部提交，其中 1,492 次获得预期的 429，所有已接收任务均成功。
6. 最后一次服务进程的指标为接收 66,728、成功 66,728、失败或超时 0、排队和运行均为 0。停止服务后，SQLite `PRAGMA quick_check` 返回 `ok`，数据库中有 287,565 条记录，文件约 700 MB。

## 结论边界与复现资料

这次完成了现有 12 阶段矩阵，并确认在本机硬件、当前工具组合与 SQLite WAL 模式下，FULL 写盘同步是显著瓶颈。NORMAL 是针对普通服务重启恢复需求的显式性能选项。高并发阶段的少量提交传输错误、阶段间复用数据库、网络路径变化，以及缺少三次交错重复和冻结的延迟预算，均不满足 `PLAN.md` 的正式稳定容量判定条件；这些数据不能作为生产容量承诺。

本机原始结果及阶段前后指标快照保存在被 Git 忽略的 `benchmarks/generated/results/run-20261030-full-matrix/` 与 `benchmarks/generated/results/run-20261030-normal-matrix/`。其中包含私有配置，不提交到仓库。服务器保留相应数据库与日志，便于复核。后续容量确认应使用直连网络、独立新数据库和重复测量，并同时采样客户端与服务端资源。
