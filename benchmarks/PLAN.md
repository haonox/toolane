# Toolane 引擎压测方案

## 1. 目标与结论边界

目前不知道未来业务会接入哪些工具，因此本方案不假定一组“真实业务请求”。测试使用可复现的工具类型，测量 Toolane 在指定硬件、配置和输入下的容量边界、延迟、租户隔离、持久化成本及过载行为。报告应给出“条件 + 指标 + 置信程度”，不能只给一个通用的每秒请求数。

本方案的基本单位是**一次完整工具调用**：客户端提交 HTTP 请求，获得执行 ID，轮询到终态并校验结果。一次调用会经历认证、准入、SQLite 持久化、租户调度、Worker、独立 Python 进程和结果读取。1000 个 Token 代表 1000 个调度租户，不等于 1000 个终端用户。测试到的上限也包含 Python 启动成本和轮询流量；若未来使用不同工具运行方式，必须重新测量。

压测分成两个可独立复现的系列：**容量系列**每个场景使用新数据库和受控初始状态；**增长系列**在同一数据库上持续提交、重启和复测。两类结果不得合并成同一条容量曲线。当前 `config/stages.json` 在并发阶梯中间插入了 10 万次调用，会使后续阶段受数据库及进程状态增长影响，不能直接用于独立并发容量比较。

## 2. 当前基线与待补能力

现有 `config/workload.json` 为文本 40%、哈希 20%、等待 30%、报告 10% 的**假设性组合**。其参数为固定档位，选择顺序可复现。`bench.lookup` 只休眠 10/80/300 ms，不访问外部系统；`bench.report` 生成 JSON，不进行查询。四个工具可测引擎处理不同耗时和输出形态的表现，不能证明真实数据库、网络、限流或重试场景的表现。

现有 HTTP 客户端支持闭环并发、固定到达率、热点租户选择、提交/终态/延迟统计，并按工具、场景和租户统计数量。可选诊断配置已增加 no-op、本地 SQLite 读取和进程失败/超时/输出超限工具，客户端可核验场景预期终态及结果字段并统计结果大小。`run.py` 只编排单机矩阵。以下方案中的受控 HTTP 网络 I/O、指定时长稳态、取消、重启一致性核验、逐租户延迟分布和周期性资源采样，仍是**待补齐的测试能力**；没有补齐前不得声称相应场景已通过。压测工具本身的改动应单独记录版本和参数。

## 3. 统一测量口径

| 指标 | 口径 |
| --- | --- |
| 计划、实际提交、接收、拒绝、终态数量 | 分别统计；`429` 不能算作成功完成，固定到达率下的 `client_capacity_drops` 是客户端未发出的请求 |
| 成功完成速率 | 成功终态数除以测量窗口时长；另外报告提交速率及阶段排空时间，避免将排空时间混入固定到达率的计划速率 |
| 延迟 | 提交、端到端、排队和执行各报 p50/p95/p99 与有效样本数；端到端包含客户端轮询间隔。用于容量判定的 p99 至少需要 1000 个有效样本 |
| 公平性 | 热点与普通租户分别报告接收率、成功率、排队和端到端 p95/p99；各组 p99 至少需要 1000 个有效样本，单租户样本不足时只报告数量和成功率 |
| 资源 | 服务与客户端 CPU、RSS、进程/文件描述符、磁盘 IOPS/写入量/同步延迟、SQLite/WAL 大小、日志量、网络吞吐；服务端队列/运行数和完成计数按固定间隔采样 |

每个阶段开始和结束都要记录排队、运行与未完成数量。正常容量阶段应从已排空状态开始；过载阶段要记录停止发压后的排空时间。服务端指标计数若因重启归零，应按进程区间计算增量，不跨重启直接相减。现有客户端只保留阶段级汇总，若要区分“加压窗口”和“排空窗口”，需先补时间窗口统计。

## 4. 场景矩阵

下表是**计划执行顺序**，不是已完成结果。每个容量档位至少重复 3 次，报告中位数和最小/最大值；若成功速率的极差超过中位数的 10%，或 p99 的极差超过中位数的 20%，先查环境漂移并重测，不取最好的一次。先用小规模链路验证，再进行容量测试，最后运行可能积累状态或产生大量失败的场景。

| 场景 | 方法与变量 | 要回答的问题 | 当前可执行性 |
| --- | --- | --- | --- |
| C0 链路与空载基线 | 每种工具低并发运行，校验结果、空载执行时间和结果字节数；增加极短 no-op 工具 | 单次调用的固定成本是多少？工具本身占多少时间？ | 四工具和可选 no-op 均可执行 |
| C1 单类型容量 | 文本、哈希、等待、报告分别运行轻/中/重档；逐级增加并发，再对选定档位做固定到达率测试 | CPU、占槽时间和结果大小分别怎样影响容量？ | 现有工具与客户端基本可执行；稳态窗口待补 |
| C2 混合负载容量 | 固定现有 40/20/30/10 组合，测试 64、128、256、512 等并发，接近拐点时缩小步长；另测两个边界组合：短任务占多数、慢任务占多数 | 混合负载的稳定容量与排队拐点在哪里？ | 默认组合可执行；边界组合需新增负载配置 |
| C3 租户规模与倾斜 | 保持总到达率与工具组合不变，比较少量/中量/1000 个活跃租户；比较均匀与 10% 租户承担 80% 调用 | 租户数量和热点是否影响吞吐、公平性？ | 当前可做 1000 租户均匀/热点；活跃租户数和逐租户延迟待补 |
| C4 突发与持续过载 | 在 C2 稳定容量附近，按固定到达率施加 1.0、1.2、1.5 倍负载，并注入短时突发；停止后观察排空 | 队列增长、`429`、延迟和恢复是否可控？ | 固定到达率可执行；短时突发和时间窗口待补 |
| C5 持久化增长 | 在同一数据库上持续调用至预定数量或时长，每隔固定调用量重复同一参考阶段；分别比较进程不重启、同库重启、全新库 | 速度下降来自数据库增长、进程状态还是其他因素？ | 可手工执行；自动采样与分段对照待补 |
| C6 故障与恢复 | 工具主动失败、超时、超限输出；排队中及运行中重启服务，核验持久化状态与恢复后处理 | 错误路径会否丢任务、重复执行或使队列无法排空？ | 故障工具与预期终态校验可执行；重启一致性核验待补 |
| C7 真实 I/O 形态 | 分别测本地 SQLite 读取与受控 HTTP 服务，后者注入延迟、错误和结果大小；不依赖公网服务 | 实际连接、序列化和失败是否改变 C1/C2 结论？ | SQLite 读取可执行；受控 HTTP 服务待补 |

可选扩展：如未来工具可能大量占用内存、返回接近大小限制的结果，增加内存占用和结果大小边界场景。参数必须低于服务配置的工具超时/输出上限，并记录实际峰值。故意超限的调用属于 C6，不能混进正常容量统计。

## 5. 判定标准

### 5.1 数据有效性门槛

以下任一条件不满足，阶段标记为**无效，需重测**，不用于推断服务端容量：客户端发生 `client_capacity_drops`；客户端 CPU、连接数或网络成为瓶颈；固定到达率的测量窗口中实际提交数偏离计划数超过 5%，或到达延迟在后半段持续上升；压测期间有其他显著负载；服务端配置、工具参数、数据库初始状态或网络路径不清楚；阶段结果与服务端接收/完成计数无法对账。若同步取数存在边界误差，须在排空后再次对账。单机结果、双机直连结果和 SSH 转发结果分别标注，不能互换。

### 5.2 正常容量门槛

为避免事后挑选有利阈值，先在 C0/C1 低负载测量后，**在正式容量加压前冻结每种负载的延迟预算**，记录在运行元数据中。若尚无业务 SLO，暂用工程比较门槛：端到端 p99 不超过该负载低负载 p99 的 3 倍，且正常阶段无 `429`、无非预期终态失败、无客户端错误或超时。这个 3 倍值只用于识别性能拐点，不是对真实业务的服务承诺；报告同时给出绝对毫秒数。若低负载 p99 本身不稳定，应先解决环境噪声，不据此设预算。

在满足数据有效性和延迟预算的前提下，观察阶段中服务端队列没有持续增长，成功完成速率能跟上实际提交速率，停止发压后全部已接收调用在约定等待上限内进入终态，才能称该档位为**稳定容量**。最高满足条件的档位与下一失败档位共同构成容量区间；不要把某次瞬时峰值当成稳定容量。正常容量阶段预期 100% 调用有可核验终态和结果；故障场景按预先注入的预期终态单独核验。

### 5.3 隔离、过载与恢复门槛

- **租户隔离**：在相同普通租户到达率和工具组合下，对照均匀与热点阶段。普通租户的成功率不下降、无非预期 `429`；其排队 p99 和端到端 p99 的变化必须给出数值。若要声明“公平性合格”，先在运行前约定可接受倍数，并保证每组样本量足够；现有数据不足时只报告观测值。
- **过载**：允许按配置出现 `429` 和延迟上升，但不得出现任务状态丢失、重复成功、无界内存/队列增长或客户端未能观测到终态。记录首次拒绝点、最大排队量、停止发压后的排空时间，以及恢复到参考负载后指标是否回到其重复测试区间。
- **持久化与恢复**：按执行 ID 对账。重启后已接收任务必须有明确可解释的状态；依据当前语义，排队任务可恢复，重启时运行/取消中的任务会转为中断，不应计为自动重试成功。逐项核验零丢失、零重复执行，并记录恢复耗时及数据库完整性检查结果。
- **故障注入**：预期失败、超时、超限的数量与实际终态逐项一致；其他正常调用的成功率与延迟单独统计。故障阶段结束后队列必须排空，服务仍可正常接收与完成新任务。

## 6. 执行纪律与报告格式

1. 固定代码提交、Go/Python 版本、工具脚本及参数、服务配置、租户数、客户端轮询间隔、机器规格、磁盘、数据库路径、网络路径和采样间隔；记录是否启用详细日志。换其中任一关键条件就另起结果组。
2. 容量系列每次使用新数据库，预热后确认队列排空，再开始测量；各档独立运行，并交错重复参考档位，以识别环境漂移。增长系列明确复用数据库，按时间或调用量切片，不把早期和晚期数据混为一个平均值。
3. 开始时先验证客户端的发压余量；若使用 SSH 隧道，结果标为“含隧道开销”，不能直接推断直连部署能力。服务端和客户端的资源曲线与阶段 JSON 同步保存。
4. 每个场景报告：计划/实际提交/接收/拒绝/各终态数，成功速率，端到端、排队、执行 p50/p95/p99，资源峰值与趋势，数据库及日志增长，重复次数与离散程度，是否达到门槛，以及主要瓶颈证据。区分测得事实、推断和未验证假设。

正式报告应分别给出各工具类型和混合负载的稳定容量区间，并说明其适用的工具耗时、输出大小、租户分布及网络条件。现有 2026-10-30 双机测试已观察到 512 并发后明显退化，但测试经 SSH 转发、多个阶段复用同一数据库，且尚未定位瓶颈；它是后续诊断线索，不能直接作为本方案的最终容量结论。
