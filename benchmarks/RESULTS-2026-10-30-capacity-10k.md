# 10,000 租户容量探索（2026-10-30）

## 目的和测试边界

这轮测试寻找当前机器、SQLite `NORMAL` 和双机访问链路下的处理能力拐点。配置 10,000 个独立租户 Token，分别测真实 Python Process 工具和零等待内置 `mock.delay`。`mock.delay` 只用于隔离工具进程成本；不能把它的吞吐量当成真实业务吞吐量。

服务端是实验室服务器，Intel Core i7-13700KF、24 个逻辑 CPU、31 GiB 内存；压测客户端是工作站。服务端业务接口监听回环地址 `127.0.0.1:18080`，由只允许压测机来源地址的临时 TCP 转发器开放 `58.199.162.181:18081`。客户端访问该端口，不经过 SSH 隧道。这个经过中低速率校验的链路仍包含一次用户态转发，所有吞吐结论都属于这条端到端链路。指标接口只在服务端回环地址监听。

服务端来自 `codex/sqlite-benchmark-optimization` 的 `ca987a5`（[PR #41](https://github.com/haonox/toolane/pull/41)），配置 `database_synchronous: "normal"`；SQLite 使用 WAL。压测配置生成器来自本地 `main` 的 `4cb4fda`，本轮将租户上限从 5,000 提高到 10,000；压测客户端增加了内置工具结果字段校验。两台机器上均使用本轮新生成的私有 Token。测试目录为两台机器上的 `/tmp/toolane-capacity-20261030/`；私有配置、数据库和原始结果没有提交到 Git。

除另有说明，服务端使用 256 workers、全局队列 4096、每租户运行上限 12、每租户待处理上限 512、内存结果保留上限 50,000。场景均匀轮转租户；固定到达率每轮使用独立 SQLite 数据库，部分闭环对照在同一数据库上接续执行，详情见各节。闭环测试为 512 个完整调用并发、每 100 ms 轮询一次；固定到达率测试的客户端在途上限为 8192、每 250 ms 轮询一次。成功数需同时满足 HTTP 接收、最终 `succeeded` 和客户端结果校验；报告中的延迟包含轮询间隔。

复现时在隔离目录复制 `benchmarks/config/` 和 `benchmarks/tools/`，将 `profile.json` 的 `tenant_count` 设为 10000、`execution.workers` 设为目标值，再从项目根目录执行 `go run ./benchmarks/prepare --root <隔离目录>`。每轮给私有 `server.json` 设置 `database_synchronous: "normal"` 和新的绝对 `database_path`。内置工具档位将所有 Token 的允许工具设为 `mock.delay`，客户端使用 `config/workload-mock-zero.json`；真实工具档位保留 prepare 生成的四个 Process 工具权限，使用 `config/workload.json` 或 `config/workload-noop.json`。客户端固定到达率参数为 `-arrival-rate <速率> -requests <速率乘以秒数> -concurrency 8192 -poll-interval 250ms -http-timeout 30s -wait-timeout 60s`；500 ms 对照只改变轮询参数。所有私有配置均只在限制权限的测试目录保存。

## 真实 Python 工具：worker 与租户规模

`bench.noop` 每次仍启动 Python 进程，给出工具进程启动和引擎合计成本。每档 50,000 次调用，10,000 个租户，闭环并发 512；所有调用成功，无 `429`、客户端丢弃或传输错误。

| workers | 成功吞吐（次/秒） | 端到端 p99（ms） | 服务端 CPU 空闲率 |
| ---: | ---: | ---: | ---: |
| 48 | 886.2 | 735 | — |
| 96 | 855.9 | 764 | 7.43% |
| 128 | 855.8 | 771 | 3.78% |
| 192 | 844.1 | 1476 | 1.97% |
| 256 | 851.9 | 772 | 1.50% |

同样条件下，四个业务 Python 工具的混合负载在 48 workers 时为 782.1 次/秒、p99 1010 ms；256 workers 时为 804.5 次/秒、p99 911 ms。单独使用 1,000 租户、48 workers 的对照为 `noop` 856.0 次/秒、混合负载 766.7 次/秒。没有观察到从 1,000 扩到 10,000 租户时显著下降，但这些闭环阶段同时活跃的调用数约为 512，不能证明 10,000 租户同时高频活跃时也没有调度开销。增加到 256 workers 没有显著提高 Python 工具吞吐；CPU 空闲率下降，说明已接近这台机器上的进程与 CPU 竞争边界。

## 零等待内置工具：隔离引擎路径

使用仓库中的 `config/workload-mock-zero.json`，结果必须含 `{"value":"ok"}`。这个场景不启动 Python 进程，也不代表真实业务结果大小；由于返回值固定，它无法单独检测跨执行 ID 的结果错配。

| workers | 完整调用并发 | 轮询间隔 | 调用数 | 成功吞吐（次/秒） | p99（ms） | 非预期错误 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 48 | 512 | 100 ms | 100,000 | 1042.3 | 572 | 0 |
| 256 | 512 | 100 ms | 100,000 | 1160.7 | 558 | 0 |
| 256 | 1024 | 100 ms | 100,000 | 940.1 | 2161 | 0 |
| 256 | 1024 | 250 ms | 100,000 | 1035.9 | 1201 | 0 |
| 256 | 512 | 100 ms，重复 | 50,000 | 1126.9 | 579 | 0 |

在 1024 并发时将轮询间隔从 100 ms 增至 250 ms，客户端 GET 总数从 954,192 降至 431,943，吞吐有所恢复。100 ms 高频轮询会给客户端、转发器和服务端增加工作量，不能把该档的下降直接归因于租户调度器。重复 512 并发测试排除了数据库增长作为 1024 并发下降的主要原因。

## 固定到达率：稳定区间和过载信号

下表均为 10,000 租户、256 workers、零等待工具和全新数据库。短档位各计划 90,000 次调用，5 分钟档位的计划次数等于速率乘以 300 秒；通过条件是所有调用接收并成功，`429`、传输错误和客户端容量丢弃均为零。`p99` 是端到端延迟，`峰值队列` 来自服务端指标采样。

| 计划速率（次/秒） | 接收/计划 | `429` | 成功吞吐（次/秒） | p99（ms） | 峰值队列 | 判定 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 900 | 90,000/90,000 | 0 | 897.7 | 425 | 79 | 通过 |
| 1100 | 90,000/90,000 | 0 | 1096.4 | 323 | 17 | 通过 |
| 1100，持续 5 分钟 | 330,000/330,000 | 0 | 1098.9 | 402 | 99 | 通过 |
| 1150，持续 5 分钟 | 345,000/345,000 | 0 | 1148.9 | 407 | 46 | 通过 |
| 1200，第一次 | 90,000/90,000 | 0 | 1195.6 | 489 | 53 | 通过 |
| 1200，第二次 | 90,000/90,000 | 0 | 1195.1 | 362 | 29 | 通过 |
| 1200，第三次 | 90,000/90,000 | 0 | 1194.4 | 351 | 20 | 通过 |
| 1175，持续 5 分钟 | 313,710/352,500 | 38,786 | 1033.9 | 5996 | 4096 | 失稳 |
| 1200，持续 5 分钟 | 316,212/360,000 | 43,486 | 1043.0 | 7871 | 4096 | 失稳 |
| 1200，500 ms 轮询，持续 5 分钟 | 304,715/360,000 | 55,238 | 968.7 | 7721 | 4096 | 失稳 |
| 1250，轮询 500 ms | 76,890/90,000 | 13,110 | 1028.9 | 5969 | 4096 | 过载 |
| 1300，第一次 | 89,547/90,000 | 453 | 1238.8 | 3830 | 3614 | 过载 |
| 1300，第二次 | 86,537/90,000 | 3457 | 1193.0 | 5134 | 4096 | 过载 |

另有一轮 1250 次/秒、250 ms 轮询出现 12,985 次 `429`、1577 次客户端容量丢弃及传输错误，客户端本身失稳，不用该轮估计吞吐上限；它和 500 ms 轮询的独立失败方向一致。1200 次/秒前三轮每轮仅持续约 75 秒；5 分钟复测在约 100 秒后开始积压，队列随后打满，累计还有 93 次客户端容量丢弃和 209 次提交传输错误。1175 次/秒的 5 分钟复测同样失稳：约第 128 秒队列超过 1000，第 139 秒开始 `429`，最终还有 4 次提交传输错误。因此 **1200 次/秒只能作为短时通过档位，不能作为持续容量**。1100 和 1150 次/秒的 5 分钟复测均全部成功，p99 分别为 402 和 407 ms，队列采样峰值分别为 99 和 46。当前 250 ms 轮询的五分钟稳定边界落在 1150 与 1175 次/秒之间。

1100 次/秒长档位的服务进程平均使用约 2.0 个 CPU 核，平均写入约 75 MB/s；NVMe 设备平均利用率约 20%，平均写等待约 1.5 ms。这些数据没有显示整个 CPU 或磁盘设备已满载，但不能排除 SQLite 单写入路径、锁竞争、日志或网络链路中的局部瓶颈。1200 次/秒失稳时，服务端队列先增长，再出现大量 `429`；需要进一步剖析具体热路径。

1150 次/秒通过档位共发起 663,121 次 GET 轮询，约 2208 次/秒；1175 和 1200 次/秒失稳档位分别发起 3,126,817 和 3,322,743 次轮询，平均每秒超过 10,000 次。由总量推断，排队延迟使轮询负载放大，可能进一步挤压任务处理能力；仅凭这些聚合数不能确定最初触发积压的是轮询还是存储写入。

将 1200 次/秒长档位的轮询间隔改为 500 ms 后，总轮询数降至 1,945,192，但仍在约 2 分钟时打满队列，最终有 55,238 次 `429`。因此降低这一档的轮询频率没有消除起始积压，不能把持续容量边界简单归因于客户端 GET 频率；这是单轮对照，仍可能有机器状态波动。

最后将租户数单独改为 1,000，其余维持 256 workers、1200 次/秒、500 ms 轮询和全新数据库。5 分钟内 279,740/360,000 次被接收并成功，80,217 次 `429`、43 次提交传输错误、零客户端容量丢弃，队列峰值 4096，p99 为 13,164 ms。1000 租户对照同样过载，所以 1200 次/秒长档位失稳不能仅归因于配置了 10,000 个租户。单轮对照不支持精确估计两种租户规模的性能差。两种配置的客户端到达滞后 p99 都约为 1 ms，提交计划本身没有明显漂移。

1175 次/秒的进程采样显示，开始积压前服务端约使用 2.1 个 CPU 核、转发器约 0.5 个核；积压后分别升至约 4.5 和 3 个核，服务进程内存也由约 150 MiB 升至 330–380 MiB。同期 NVMe 写入与等待时间没有同幅度突变。这与轮询放大和积压后的资源竞争一致，但并不证明最初的容量限制来自哪一段。

## 100 万调用、数据库增长和重启

10,000 租户、256 workers、四种真实 Python 工具的混合负载，在全新 SQLite 数据库上执行 1,000,000 次闭环调用。每个租户恰好提交并成功 100 次；全部 HTTP `202`、全部最终 `succeeded`，无 `429`、失败、超时、客户端丢弃或传输错误。整个阶段 1264.5 秒，成功吞吐 790.8 次/秒，端到端 p50/p95/p99 为 624/776/929 ms；排队 p50/p95/p99 为 265/319/354 ms。服务端采样到的队列峰值为 254，结束时队列和运行数均为 0。

按每 100,000 次完成量观察，第一段约 723 次/秒（包含预热），随后为 795、789、788，最后一段为 775 次/秒，没有持续恶化趋势。处理 100 万次后，SQLite 数据库约 2.3 GiB，服务日志约 767 MiB。`retained_results: 50000` 控制内存保留量，并不会将 SQLite 历史记录裁剪到 50,000 条；磁盘增长需要单独规划清理或归档。

正常停机后 SQLite `PRAGMA quick_check` 返回 `ok`，数据库恰有 1,000,000 条记录。服务使用原配置和原数据库重启后，HTTP GET 取回最早和最新执行记录，二者仍为 `succeeded`。重启后又在同一数据库上完成 50,000 次混合调用，全部成功、无非预期错误，吞吐 816.8 次/秒，p99 为 1386 ms。吞吐没有明显下降，尾延迟存在波动；这一次短阶段不足以证明长期 p99 稳定。这轮只验证正常停机重启，没有执行突然断电或强制终止恢复测试。

## 突发负载的有效性

尝试在 10 秒内提交 20,000 次零等待调用、客户端上限 20,000、队列 16,384，目的是覆盖更高的同时活跃租户数。单端口直连出现 629 次提交传输错误；改用四个转发端口分片后，仍有 551 次提交传输错误和 314 次轮询传输错误，因此两轮都**不能用于推断引擎的突发容量**。服务器本机回环诊断完成 20,000 次提交，18,672 次接收并成功、1,328 次 `429`、无传输错误；队列接近 16,384，说明过载保护和排空路径工作，但同机客户端会争用服务端资源，不能代替双机结果。

## 结论与下一轮方向

在这台实验室服务器上，四个 Python 业务工具的当前混合吞吐约 800 次/秒；零等待内置工具、10,000 租户、256 workers、250 ms 轮询在 1150 次/秒持续 5 分钟全部通过，1175 次/秒失稳。1200 次/秒的 75 秒短档位连续三轮通过，但同一速率 5 分钟测试失稳；将轮询间隔加倍或将租户数降至 1000，均未使其稳定。当前不能将 1200 次/秒报告为持续容量。10,000 租户均在 100 万次阶段真实产生了调用，但本轮没有完成有效的 10,000 租户同时突发双机测试。

下一步应先剖析 SQLite 单连接状态写入和管理器锁的耗时，再分别量化 Python 进程启动、HTTP 轮询及临时 TCP 转发器的成本。改善突发测试链路后，再对更高同时活跃租户数和更大 SQLite 数据库复测。真实业务工具耗时和结果大小确定后，应以该分布重设负载；长期运行还需处理数据库和日志的磁盘增长。
